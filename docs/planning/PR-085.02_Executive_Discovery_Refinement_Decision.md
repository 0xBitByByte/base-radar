## 1. Executive Review

This PR's four objectives are all answerable from data Base Radar
**already fetches today** — the central, load-bearing finding of this
audit. CoinGecko's bulk markets call
(`lib/providers/coingecko/client.ts:41,58`) already requests
`price_change_percentage=24h,7d,30d` and already maps a `changePct7d`
field (`lib/providers/coingecko/mapper.ts:51`) — but `lib/projects/build.ts`
(lines 71, 195) only threads `changePct24h` onto `LiveProject.market`,
dropping the already-fetched 7-day figure on the floor. This means
Objective 2's momentum signal is achievable with a mapping change, not a
new provider request — directly satisfying this PR's own Performance
constraint before any implementation is even proposed.

Objective 1's secondary-metric question resolves cleanly once the
existing `categoryPrimaryMetric()` logic (`lib/projects/primaryMetric.ts:27-34`)
is read directly: only **FDV** and **Liquidity** are structurally never
selected as any category's primary metric (TVL/Volume/Market Cap are each
primary somewhere, Price is the universal fallback) — so only those two
are candidates for a secondary metric that never duplicates the primary.
Research (§3 below) and a direct evaluation of data availability across
categories both favor **FDV**.

Objective 3 surfaces a real, honest gap rather than a clean answer: the
codebase's one existing AI-outputs-derived recommendation vocabulary
(`RECOMMENDATION_FOR_RISK`, `lib/intelligence/report.ts:153-158`) has only
three distinct phrases, driven by Risk Level alone — it does not, and
cannot without new logic, produce the seven-term vocabulary
(Research/Watch/Accumulation/High Conviction/Monitor/Speculative/Avoid)
the directive lists as an example. Per this PR's own explicit instruction
not to fabricate, §5 below documents this gap rather than inventing a
mapping.

Objective 4 concludes that the requested row order would require
restructuring the Universal Project Card Standard's own frozen §6 One
Question Per Row structure — which this PR's own Consistency Rules
require respecting — so the recommended refinement is the smallest
possible: none to the DOM/row order, with the reasoning documented in §6
below so a future reviewer doesn't re-litigate it without this context.

## 3. Secondary Metric Recommendation

**Recommendation: FDV (Fully Diluted Valuation), shown only when
`market.fdvUsd` is non-null.**

**Research basis:** FDV vs. Market Cap is a well-established, standard
investor comparison in crypto specifically — the Market Cap/FDV ratio is
widely cited as "the cleanest single number for a quick dilution check"
(a ratio near 1.0 signals most supply already circulating and low
dilution risk; a ratio below 0.2 signals high dilution risk), and FDV is
specifically valued as "a metric for comparing different crypto projects
on a more equivalent basis... when evaluating projects at different
stages with varying token release schedules." This directly answers the
directive's own instruction to research what investors naturally compare
— FDV is not a Base-Radar-specific choice, it's the metric the wider
industry already uses for exactly this horizontal-comparison purpose.

**Why not the other four candidates:**
- **24h Volume** — already the primary metric for `dex`/`bridge`
  categories (`primaryMetric.ts:29-30`); showing it as a secondary metric
  on those categories' own cards would duplicate the primary field,
  which the Universal Card Standard's own §24 Evolution Rules (check 4:
  "does it duplicate a signal already on the card") explicitly prohibits.
- **Market Cap** — same problem for `stablecoin`/`infrastructure`/`ai`
  categories (`primaryMetric.ts:31-33`).
- **Liquidity** — structurally never primary (a valid candidate on that
  basis alone), but DEX liquidity depth is most meaningful for
  categories that are *already* volume-primary (`dex`/`bridge`) and is
  frequently null for the categories where Market Cap is primary
  (Infrastructure/AI/Stablecoin tokens without a liquid DEX pair) — the
  categories that would most need a non-redundant secondary metric are
  exactly the ones where Liquidity is least likely to have real data.
- **Users** — confirmed absent from `LiveProject`/`MarketSummary` and
  every provider this app integrates (per the Standard's own §8 audit);
  would require fabricating a field, prohibited by this PR's own
  Performance constraint against workarounds.
- **Transactions** — belongs to Whale/Contracts Explorer depth (per the
  Standard's own §8 tiering), and per
  [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)'s own §22 Performance
  Budget research (Universal Card Standard), would require a genuine
  per-contract fetch multiplied across every card — explicitly the kind
  of per-card fetch this PR prohibits.

**Data availability:** `market.fdvUsd` is already a field on
`LiveProject.market` (`lib/projects/types.ts:46`) — already threaded
through `build.ts`, already rendered nowhere on any discovery card today
despite being fully available. This is the cleanest possible case: zero
new fetch, zero new field, only a new render decision.

## 4. Momentum Recommendation

**Recommendation: 7-day price change (`changePct7d`), shown alongside —
not replacing — the existing 24h change where both exist; 24h remains the
figure shown when only 24h is available.**

**Why 7-day over the directive's other listed candidates:**
- **TVL growth / Volume growth** — both require the DefiLlama TVL-history
  provider call this codebase's own Project Profile page already
  identifies as its single slowest, most expensive fetch
  (`components/explorer/ProfileTvlChartAsync.tsx`'s own doc comment,
  observed 4-25s per [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)'s
  citation) — multiplying that call across every card in a discovery grid
  would be a severe, explicit violation of this PR's per-card-fetch
  prohibition and of the Universal Card Standard's own §22 Performance
  Budget, which already names this exact scenario as disqualifying.
- **User growth** — the underlying `Users` field doesn't exist at all
  (§3 above); a growth rate over a nonexistent base field is not
  computable honestly.
- **Revenue growth** — Revenue itself is not a real, sourced field on
  `LiveProject` today (confirmed absent in the Standard's own §8 audit);
  same disqualification.
- **Developer growth** — GitHub commit activity (`commitsLast7d`,
  `lib/projects/types.ts:65`) does exist cheaply on `LiveProject` already
  (bulk-fetched, not per-card), but it measures engineering activity, not
  market momentum — conflating the two would answer a different question
  than "is money flowing into it / is it growing" (the Standard's own §5
  questions 4-5), and risks duplicating the Universal Card's own separate,
  already-planned secondary-metrics row treatment for GitHub activity.
- **24h % alone (status quo)** — the directive's own framing ("static
  values do not answer 'is this growing'") is not fully accurate: 24h
  change already answers a narrow version of that question. The real gap
  is that 24h is a single, volatile snapshot, not a trend — a project can
  show +15% on one bad-then-good day and read as "growing" when it's
  actually flat over the week, or vice versa. 7-day change is the
  standard second data point that turns a snapshot into a trend read,
  without requiring a new fetch.

**Data availability, confirmed with exact evidence:** `changePct7d` is
already parsed in `lib/providers/coingecko/mapper.ts:51`
(`raw.price_change_percentage_7d_in_currency`), sourced from a request
parameter (`price_change_percentage=24h,7d,30d`) already present in both
CoinGecko client calls used by the bulk ecosystem fetch
(`lib/providers/coingecko/client.ts:41,58`). `lib/projects/build.ts`
simply never reads this already-parsed field onto `LiveProject.market` —
confirmed by its own lines 71/195 threading only `changePct24h`. Adding
`changePct7d: market.changePct7d` to `MarketSummary` and `build.ts`'s
market-mapping block is a type/mapping change against data the app
already has in memory during the same batch build — **zero new provider
requests**, satisfying this PR's Performance constraint exactly as
written, not as a best-effort approximation of it.

**"One concise signal, not overloaded"**: per the directive's own
instruction, this recommendation is *one* figure (7d), shown once, in the
same slot 24h occupies today — not a second, separate momentum row. Where
a card's density tier already shows 24h (the 4 `detailed`-tier surfaces
per §2's table), 7d replaces or accompanies it in that same single Metric
row, never a new row — consistent with the Universal Card's own §14
Cognitive Load Budget, which caps `detailed` at 5 simultaneous numeric
values and does not have room for a second, independent momentum figure
without displacing something else.

## 5. AI Recommendation Strategy

**No new vocabulary is recommended. The existing `RECOMMENDATION_FOR_RISK`
phrases should be the discovery card's Recommendation field, used
verbatim — and the gap to the directive's fuller vocabulary is documented
below rather than closed by invented logic.**

**What exists today**, read directly from `lib/intelligence/report.ts:153-158`:

```
RECOMMENDATION_FOR_RISK: Record<RiskLevel, string> = {
  low: "Suitable for Deeper Research",
  moderate: "Monitor Closely",
  elevated: "Monitor Closely",
  high: "Exercise Caution",
}
```

Three distinct phrases (moderate/elevated collapse to the same string),
driven entirely by Risk Level — already computed, already displayed
elsewhere in the app (the AI Intelligence Report page, per this
initiative's own prior research), and already exactly the phrase
vocabulary the Universal Card Standard's own §11 names as the card's
correct AI Recommendation source ("reuse that existing phrase vocabulary
verbatim — one AI voice across the product, not a second one invented for
the card").

**Mapping this onto the directive's requested vocabulary, honestly:**

| Directive's term | Maps to an existing output? | Basis |
| --- | --- | --- |
| **Research** | Yes — "Suitable for Deeper Research" (low risk) | Direct, existing string |
| **Monitor** | Yes — "Monitor Closely" (moderate/elevated risk) | Direct, existing string |
| **Avoid** / **Speculative** | Partially — "Exercise Caution" (high risk) is the closest existing output, but is deliberately softer than "Avoid" | The codebase's own risk-communication philosophy (per `RISK_MEANING`, `lib/intelligence/report.ts:273-278`) is calibrated to describe uncertainty, not issue directives — "Avoid" is an instruction, "Exercise Caution" is a description. Relabeling it "Avoid" would be a wording change with real editorial-tone consequences, not a data mapping; not proposed here without Product Owner sign-off specifically on that tone shift |
| **Watch** | No existing distinct output — collapses into "Monitor Closely" today | Gap |
| **Accumulation** | **No.** Nothing in the current AI/Risk/Confidence pipeline computes a forward-looking buy-signal. Fabricating one would mean inventing new scoring logic this PR's own instructions explicitly prohibit | **Documented gap, not filled** |
| **High Conviction** | **No.** Same reasoning — this term implies a confidence-weighted recommendation the current pipeline doesn't compute (Confidence Score measures data trust, not investment conviction, per this initiative's own Good Project Evaluation Framework's explicit distinction) | **Documented gap, not filled** |

**Recommendation:** ship the existing 3-phrase vocabulary on the
`detailed` tier's discovery cards (already rendered there today per §2's
table — no change needed on that tier) and, if `compact` gains a
Recommendation field per §2's identified gap, use the same 3 phrases,
not a new set. Do not introduce Watch/Accumulation/High Conviction/
Speculative/Avoid without a separate, explicit Product Owner decision to
either (a) accept "Exercise Caution" standing in for both Speculative and
Avoid, or (b) commission new scoring logic to genuinely distinguish them —
option (b) is out of scope for a refinement PR and would itself need to
route through the Good Project Evaluation Framework's own Evidence
Hierarchy before any new score could be trusted.

## 6. Trust Hierarchy Review

**Recommendation: no change to row order. The requested sequence is not
adopted, and the reasoning is documented here so it isn't re-litigated
without this context.**

The directive's proposed order (Identity → Verification → AI Rating →
Risk → Primary Metric → Momentum → Recommendation) differs from the
current, frozen implementation
(Identity → Trust cluster → AI Rating+Recommendation → Primary Metric+
Category Rank → Risk+Status → secondary metrics) in one specific way:
it asks for Risk to move earlier, ahead of the Primary Metric, splitting
it from its current pairing with Project Status.

**Why the smallest refinement is none, not a reorder:** the Universal
Project Card Standard's own §6 (One Question Per Row) pairs Risk Badge
and Project Status into one Status row specifically because both answer
the same underlying question — "is anything urgent" — and that pairing is
a frozen, already-approved design decision, not an accident of
implementation order. Moving Risk alone would either (a) break that
pairing, leaving Project Status stranded in its own row (a genuine
restructure, prohibited by this PR's own "do not redesign the layout"
instruction and by the Universal Card Standard's own §25 "restructuring
is reserved for correcting a real design flaw, not for accommodating one
more field"), or (b) move both Risk and Status together, which is a
larger change than the directive asked for and isn't justified by
anything this audit found.

**The requested intent is already substantially satisfied at the
*perceptual* level, even though the DOM order differs:** per the
Universal Card Standard's own §13 Visual Hierarchy Rules, Risk Badge,
Trust Indicators, and Project Status are all **Rank-2** elements —
"sized to be scannable in a row," rendered near the top of the card
alongside the Rank-1 AI Rating grade — while a discovery card is scanned
as a whole glance, not read top-to-bottom like prose (this is the entire
premise of this Standard's own Five-Second Rule, §6 of
[EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)).
A user's eye reaches Risk in the same first-second sweep as Trust and AI
Rating regardless of whether it's the 2nd or 5th row in the DOM, because
none of those elements requires reading the rows in between to be
noticed. The genuine gap this audit did confirm is not row *order* but
row *presence* — `compact`'s missing Recommendation/Momentum fields (§2) —
which is already addressed by §3/§4 above without touching row order at
all.

## 8. Performance Impact Assessment

**Net new provider requests: zero.** Every recommendation in this
document (FDV as secondary metric, 7-day price change as momentum, the
existing 3-phrase Recommendation vocabulary) uses a field that is either
already on `LiveProject` (`fdvUsd`) or already fetched and parsed but not
yet threaded onto it (`changePct7d`) or already computed and rendered
elsewhere (`RECOMMENDATION_FOR_RISK`). No new fetch, no new per-card
request, no new provider integration is required by anything recommended
here — directly satisfying this PR's Performance section as written.

**Render cost:** adding two already-available fields (FDV, 7d change) to
`compact`'s existing Metric row, and one already-computed string
(Recommendation phrase) if budget allows, is a formatting/display change
against data already in memory during the same render pass — no new
computation loop, no new sort/filter pass, and no interaction with the
unmemoized-pass findings [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)
already flagged separately (H1 there remains a distinct, already-recorded
issue this PR doesn't touch).

**Documented data gap, not implemented as a workaround (per this PR's own
instruction):** a genuine Watch/Accumulation/High-Conviction/Speculative
distinction (§5) would require new scoring logic — explicitly not
attempted here. TVL/Volume/User/Revenue/Developer *growth* rates (§4)
would require either a new expensive fetch (TVL/Volume growth) or a
nonexistent underlying field (User/Revenue growth) — explicitly not
attempted here either.

## 9. Implementation Roadmap

**Not authorized for implementation by this document.** Recorded as a
sequencing plan only, for Product Owner approval:

### Phase 1 — Data threading (no visual change yet)
1. Add `changePct7d: number | null` to `MarketSummary`
   (`lib/projects/types.ts:41-50`).
2. Thread `market.changePct7d` through `lib/projects/build.ts`'s existing
   market-mapping blocks (lines 71, 195), mirroring exactly how
   `changePct24h` is already threaded.
3. Verify `fdvUsd` is already correctly populated for a representative
   sample of registry projects (spot-check, not a new fetch — confirming
   existing data, not adding any).

### Phase 2 — `compact` tier field additions
1. Add FDV to `compact`'s existing metric-display logic as the secondary
   value, gated on `market.fdvUsd !== null`.
2. Switch the Momentum figure shown (where already present at `detailed`,
   and newly added at `compact`) from `changePct24h` to `changePct7d`,
   with a fallback to `changePct24h` when 7d is unavailable but 24h is —
   never show neither when either exists.
3. Evaluate, against the Universal Card Standard's own §14 Cognitive Load
   Budget for `compact`, whether a Recommendation phrase fits within the
   existing row/badge ceiling — if it does not, defer this specific
   sub-item and record it as a Future Enhancement rather than exceeding
   the budget.

### Phase 3 — Verification
1. Static verification (tsc/lint/build), per
   [CLAUDE_PR_WORKFLOW.md](../CLAUDE_PR_WORKFLOW.md).
2. Live browser QA: confirm FDV/7d-change render correctly (including the
   `null`-fallback paths) across `detailed` and `compact`, across
   light/dark and mobile/desktop, and confirm no card exceeds its tier's
   Cognitive Load Budget after these additions.

**Explicitly out of scope for this PR**, consistent with §2/§7's findings:
any change to `micro`, Search, Base Today, Recommendations, Portfolio
rows, or Alerts; any new AI-recommendation vocabulary beyond the existing
3 phrases; any row-order change to any tier.
