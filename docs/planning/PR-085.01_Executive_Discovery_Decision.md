# PR-085.01 — Executive Project Discovery Experience — Product Decision Document

**Status:** Research and audit only. No implementation is authorized by
this document. This is a Product Decision document, not a roadmap PR — it
becomes an implementation roadmap only after explicit Product Owner
approval of the decisions recorded here.

This document answers the three problems named in the PR-085.01
directive, using [EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)
as source of truth throughout — every recommendation below cites the
section of that Standard it derives from, rather than proposing anything
independently.

---

## 1. Executive UX Review

The Projects page's first impression suffers from two independent, real
problems, both confirmed in code:

**Loading feels slow because it is fully blocking, not because the
underlying work is unusually slow.** `app/dashboard/projects/page.tsx`
`await`s `loadProjectsPageData()` synchronously before any JSX renders —
no `Suspense`, no partial render, no streaming. The single visible signal
during that wait is one static message, "Resolving trusted providers…"
(`app/dashboard/projects/loading.tsx:12`). [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)'s
own H1 finding already measured part of that wait's real cost:
`buildCollections()` performs 10 unmemoized full-array passes, plus
`loadProjectsPageData()` adds roughly 12 more for its 5 leaderboards and 2
smart-view lists — all before the page can show anything at all.

**Cards optimize for completeness, not decisions, on 9 of the app's 13
project-identity surfaces.** [EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)'s
§3 audit found only 4 surfaces (Projects Directory, Collections, Related
Projects, `ProjectSpotlight`) show the full executive signal set (Trust,
AI Rating, Risk, Momentum). The Projects Directory itself — the surface
this PR targets — is one of the 4 that already does this correctly at the
`detailed` tier; the real card-hierarchy problem on *this* page is Category
Rails (`ProjectRail`, `compact` tier), which shows Trust/AI-Rating/Risk but
never Momentum — the single field this Standard's own research (§10 there)
ranks as the strongest positive click-driver once Trust has cleared its
bar.

## 2. Information Hierarchy Review

Applying [EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)
§5's Executive Question Order to the two card tiers this PR's scope
actually touches:

| Question | `detailed` (Projects Directory) | `compact` (Category Rails) |
| --- | --- | --- |
| 1. What is this? | Yes (logo, name, category, chains) | Yes (logo, name only — no chain badge/category at `compact`, per the Universal Card's own frozen anatomy) |
| 2. Can I trust it? | Yes (full `TrustIndicators`) | Yes (`TrustIndicators isCompact`) |
| 3. AI opinion? | Yes (grade + recommendation phrase) | Grade only, no phrase (correct per `compact`'s Tier restrictions) |
| 4. Capital signal? | Yes (primary metric, emphasized) | Yes (primary metric, `bare` styling) |
| 5. Is it growing? | **Yes, conditional** on `changePct24h` existing | **No — `compact` never shows this today** |

This confirms PR-085.01's Problem 2/3 premise precisely for Category
Rails, and shows the Projects Directory's own `detailed` cards already
satisfy the requested hierarchy (Identity → Trust → AI Opinion → Primary
Metric → Momentum) with the sole caveat that Momentum is conditional on
data availability, not a hierarchy defect.

## 3. Recommended Card Hierarchy

**No new component and no new variant.** Per
[EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)
§12's own consistency check against the Universal Project Card Standard's
§25 Future-Proofing Rules, the correct fix is a field addition within the
existing `compact` tier, not a new card shape:

- **Keep** `detailed` for the Projects Directory and Collections — already
  correct.
- **Add** a Momentum/Growth indicator to the `compact` tier's Metric row,
  matching `detailed`'s own existing conditional-on-`changePct24h`
  pattern — this is the one concrete card-hierarchy change this PR's scope
  actually requires, per the Standard's own §13 Future Enhancement #3.
- **Do not** add a secondary-metric row, ecosystem-role tag, or Category
  Rank to `compact` — per the Standard's §7/§8 tiering, none of those are
  Tier 1/2 fields, and adding them would violate the Universal Card's own
  §14 Cognitive Load Budget for `compact` (4-row cap).
- **Category Rank remains unimplemented** on this PR's surfaces — per the
  Standard's own §13 Future Enhancement #4, `categoryPeers` is unwired
  everywhere today; wiring it is a separate, larger decision this PR does
  not need to make to satisfy Problem 2/3.

This satisfies "one clearly dominant primary metric, one consistent
secondary metric" from the PR-085.01 directive: the primary metric stays
category-aware (unchanged, per the directive's own instruction not to
remove it); Momentum becomes the consistent secondary signal across every
category, since it's a universal percentage regardless of what the
primary metric measures — exactly the "consistent across project types"
property the directive asks for, without introducing a second,
project-type-specific metric that would reintroduce the scanability
problem Problem 2 describes.

## 4. Loading Improvements

Per [LOADING_STRATEGY.md](../LOADING_STRATEGY.md)'s Route Loading Standard
and Progressive Rendering Standard, applied to this specific route:

- **Never block the entire page** — replace the single synchronous
  `await loadProjectsPageData()` with a promise-threading pattern
  (matching the Project Profile page's own established fast-path/slow-path
  precedent): the page shell, navigation, and page title render
  immediately; each data-dependent section streams in behind its own
  `Suspense` boundary.
- **Priority order** (exactly as specified in the PR-085.01 directive, and
  consistent with [INFORMATION_HIERARCHY_STANDARD.md](../INFORMATION_HIERARCHY_STANDARD.md)'s
  Executive Information Order):
  1. Page shell (nav, title, filter chrome) — no data dependency, renders
     instantly.
  2. Base Today — its own aggregate stat tiles and 3 `SpotlightCard`s are
     a smaller, faster query surface than the full collections/leaderboard
     build; a natural first data-dependent boundary.
  3. Executive summary — whatever compact ecosystem-overview content
     precedes the category sections.
  4. Category sections (the `ProjectRail` zones: Curated Discovery,
     Leaderboards, Needs Your Attention).
  5. Remaining collections / the full Directory grid — the largest,
     slowest-to-build section, correctly last.
- **Realistic skeletons, matching final card sizes** — per
  [LOADING_STRATEGY.md](../LOADING_STRATEGY.md)'s Skeleton Standard, this
  means a genuine `WidgetSkeleton`/card-shaped placeholder sized to match
  `detailed`/`compact` card dimensions, not a generic block — directly
  correcting that Standard's own H2 finding (confirmed skeleton/content
  size mismatches elsewhere in the app) by not repeating the same mistake
  here from the start.
- **Never fullscreen after navigation** — per the directive's own
  requirement and consistent with `LOADING_STRATEGY.md`'s Route Loading
  Standard, `app/dashboard/projects/loading.tsx`'s current fullscreen
  `BrandLoader` fallback should only fire on the very first navigation
  into the route (matching Next.js's own `loading.tsx` semantics); the
  progressive-streaming redesign above is what prevents subsequent,
  filtered/paginated views within the same route from re-triggering it.
- **No fake data, no artificial delay** — explicitly reaffirmed; every
  skeleton must resolve to genuinely-fetched data, and no `setTimeout` or
  similar should ever be introduced to "smooth" the perceived transition —
  this would violate [DESIGN_SYSTEM_LOCK.md](../DESIGN_SYSTEM_LOCK.md)'s
  own "honest presentation" principle and the Universal Card Standard's
  §19 Empty Data Philosophy.

## 5. Streaming Strategy

Concretely, per [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)'s own H1
finding and [LOADING_STRATEGY.md](../LOADING_STRATEGY.md)'s Streaming
Standard:

- `loadProjectsPageData()` currently builds `collections` (10 passes),
  5 leaderboards, and 2 smart-view lists as one synchronous unit. These
  should be split into independent promises, each threaded down to the
  section that consumes it, so Base Today's data doesn't wait on the full
  Directory grid's data to resolve, and vice versa — matching the Project
  Profile page's own `commitActivityPromise`/`tvlHistoryPromise`-style
  pattern, not inventing a new one.
- This is additive to, not a substitute for,
  [PERFORMANCE_AUDIT.md](../PERFORMANCE_AUDIT.md)'s own Phase 1
  recommendation to memoize/reduce the 10+12 unmemoized passes themselves
  — streaming changes *when* the cost is paid and how it's perceived;
  reducing the pass count (already a separate, approved-for-research-only
  recommendation in that audit) changes how large the cost is. Both are in
  scope for this PR's eventual implementation, not competing alternatives.

Directly reusing [EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)
§7/§8's tiering, restated here for this PR's specific surfaces only:

| Tier | Projects Directory (`detailed`) | Category Rails (`compact`, post-fix) |
| --- | --- | --- |
| 1 | Logo, Name, Trust, AI Rating grade | Logo, Name, Trust (compact), AI Rating grade |
| 2 | Primary metric, Momentum | Primary metric, **Momentum (new)** |
| 3 | Chains, Category, Risk Badge, Status | Trust+Status merged row (existing `compact` anatomy), Risk Badge |

the directive's explicit "the goal is NOT to show more data... it is to
show better data" instruction: the only change is Category Rails gaining
one Tier-2 field it was structurally missing, not a rebalancing of what's
already correct on the Directory.

the requested hierarchy per §2's table above; no before/after delta.

**Category Rails (`compact` tier):**

| | Before | After |

## 8. Implementation Roadmap

**Not authorized for implementation by this document.** Recorded as a
sequencing plan only, for Product Owner approval before any code change:

### Phase 1 — Loading (highest user-visible impact, lowest design risk)
1. Split `loadProjectsPageData()`'s outputs into independently-resolvable
   promises.
2. Restructure `app/dashboard/projects/page.tsx` to render its shell
   synchronously and thread each promise into its own `Suspense` boundary,
   in the priority order from §4.
3. Build correctly-sized skeleton fallbacks for each boundary (Base Today,
   Executive Summary, each Category section, the full Directory grid),
   per [LOADING_STRATEGY.md](../LOADING_STRATEGY.md)'s Skeleton Standard.
4. Verify `app/dashboard/projects/loading.tsx`'s fullscreen fallback still
   fires correctly only on first navigation, not on subsequent
   filter/pagination interactions within the route.

### Phase 2 — Card Hierarchy (Category Rails only)
1. Add the Momentum/Growth field to `LiveProjectCard`'s `compact` variant
   branch, gated on `changePct24h` existing — matching `detailed`'s
   existing conditional exactly, not a new pattern.
2. Verify against the Universal Card Standard's §14 Cognitive Load Budget
   (`compact`'s existing row/badge/numeric-value caps) that this addition
   doesn't exceed any ceiling — per that Standard's own §24 Evolution
   Rules, this should be a straightforward pass since Momentum fills an
   already-reserved numeric-value slot `detailed` already uses.

### Phase 3 — Verification
1. Static verification (tsc/lint/build), per this initiative's own
   [CLAUDE_PR_WORKFLOW.md](../CLAUDE_PR_WORKFLOW.md).
2. Live browser QA: confirm streaming order matches §4's priority list,
   confirm no layout shift between skeleton and resolved card (per
   [LOADING_STRATEGY.md](../LOADING_STRATEGY.md)'s own H2 finding — this
   PR should not repeat that mistake), confirm Momentum renders correctly
   on `compact` cards across light/dark and mobile/desktop.

**Explicitly out of scope for this PR**, per
[EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md](../EXECUTIVE_PROJECT_DISCOVERY_STANDARD.md)'s
own §13/§14: fixing Recommendations/Portfolio-rows/Alerts' missing
executive signals (a separate, larger decision spanning surfaces beyond
the Projects page), wiring Category Rank, and any investor/trader
discovery-mode work.
